## A. Auth architecture (verified)
Single chokepoint: `app/services/auth.py::get_current_user` (re-exported via `app/api/deps.py`) resolves Bearer JWT (HS256, typ-checked) or personal API key to a `User`, enforces email verification, then `_workspace_principal` (auth.py:181) maps an `X-Workspace-Id` header to the workspace owner with role checks via `app/services/rbac.py`. `require_admin` (deps.py:18) gates on `users.is_admin`, refuses API keys, checks the real actor; `is_admin` grantable only via CLI (`app/cli/create_admin.py`) or `ADMIN_EMAIL` bootstrap — signup drops it. **House rule** (tests/test_crm_api.py:1-7; app/api/leads.py:34-60): ownership runs lead → strategy → product → `Product.user_id` via `_owned_*` helpers (mirrored in `app/services/crm_service.py`), and foreign resources answer **404, never 403**. `app/services/notifications.py:293-322` centralizes recipient resolution after two shipped cross-tenant bugs (both since fixed: ui_support shadowed route; global email reply-matching, fixed tenant-scoped in `outreach_tasks.py:868-907`).

## C. Findings (each spot-verified at the cited lines)

### SUSPECT-HIGH — proposed CRITICAL under the register's cross-user-data default (final severity: Claude Project)
**F1. WhatsApp inbound matched to a lead by phone across ALL tenants** — `app/api/webhooks_whatsapp.py:316-325`: `select(Lead).where(Lead.phone.isnot(None))`, then first normalized-phone match wins; `phone_number_id` is stored (`account_ref`) but never used to pick the tenant. Consequence: when two tenants hold the same phone number, a private inbound reply attaches to the **wrong tenant's** lead (content disclosure), opens their 24h window, flips their lead to REPLIED, and a STOP suppresses the wrong account's sequences. This is the **third instance** of the exact class `notifications.py:300` warns "has shipped twice" — the email variant was fixed (`outreach_tasks.py:868-907`); the phone variant was not.

**F2. Website builder: shared NULL-workspace pool; global pages writable by every user** — `app/api/website_builder.py:182-211`: users owning no workspace all share the `workspace_id IS NULL` pool; `_visible_pages_filter` includes NULL pages for everyone, and `_owned_page` treats every *visible* page as *actionable*. Consequence: (a) workspace-less tenants can read/regenerate/publish/unpublish each other's pages; (b) any authenticated user can edit and publish the deployment's own marketing pages (models.py:3396-3397: NULL = "the leadpilot.io marketing site itself").

**F3. Cross-user write via onboarding complete-step** — `app/api/onboarding.py:110-133`: `CompleteStepRequest.user_id` is accepted from the body and used unchecked: `target_user_id = body.user_id or str(current_user.id)`; `mark_complete` raw-UPDATEs that user's `onboarding_state` (replacing the JSON — can also erase a victim's progress). The docstring's "only the server … or the user themselves" is not enforced by any code.

**F4. Global suppression list: cross-tenant PII read + irreversible cross-tenant write** — `app/api/ui_support.py:268-301`: GET `/suppression` returns **every** tenant's suppressed emails/phones (PII) to any logged-in account; POST lets any tenant permanently suppress arbitrary addresses deployment-wide ("no delete endpoint" by design). Global *enforcement* at send time is the right compliance posture; the unscoped *listing* and unscoped *permanent add* exceed what that goal needs and hand every tenant a read of others' opt-out PII and an irreversible block on others' outreach.

**F5. WhatsApp templates deployment-global: cross-tenant read/edit/submit, incl. drafts from private research** — `app/api/whatsapp_templates.py:96-106` documents "deliberately NOT owner-scoped" (one Meta WABA per self-hosted install); list/edit/submit are open to every logged-in tenant (:129-186); yet `POST /generate` ownership-checks a strategy *because its research is private*, then writes the derived drafts into the shared table. Defensible single-tenant self-hosted; a content leak on the multi-tenant SaaS. Also surfaced via `sequences.py:172-182` (echoes any template's name + rejection_reason).

### SUSPECT-LOW (needs deployment-context or is entropy/secret-mitigated)
**F6.** Meeting-transcript webhook: deployment-wide secret can append transcripts to **any** meeting id — the code itself says a valid signature proves "a trusted integration, not an integration entitled to this meeting" (`meetings.py:512-557`). Fail-closed without secret (503) is correct.
**F7.** FCM token transfer: register re-binds a known token cross-user (`devices.py:89-96`) — mitigated by token entropy; intentional for device wipes; consequence is misrouted push + silent DoS of the victim's notifications.
**F8.** Playbook learning aggregates are cross-tenant by design (`PlaybookScore` has no `user_id`; upsert keyed `(pattern_key, variant)`); small statistical disclosure. **Latent bug (verified):** `admin.py:291` filters `ps.user_id` on that column-less table — the query fails and `except` (:310-312) silently returns `{"scores": []}`, so the admin per-user view is permanently empty.
**F9.** Debug router residual: `POST /debug/set-send-cap` (no auth, mutates process-global Settings for every tenant) and `GET /debug/whatsapp-status` (no auth); triple guard blocks only env names {production, prod, live} — a real-data environment named `staging` with `ENABLE_DEBUG_ROUTES=true` exposes them, incl. unsubscribe-token minting (`debug.py:73, 429-443, 541-570, 799-815`; guard verified in `production_guard.py:36` + boot check `main.py:281-293` + `scripts/verify_debug_router_guard.py`, which passes only on 404).

### HARDENED (controls verified working — record, don't relitigate)
Single auth chokepoint + verification gate; CLI-only admin grant; house-rule helpers with uniform 404s; Calendly quarantine-over-guess tenant resolution; Gmail inbound now tenant-scoped (the fixed prior bug); debug triple guard + boot verification script; all public webhooks signature/token-gated fail-closed; SSE single-use tickets; TokenStore strictly `user_id`-keyed, Fernet-encrypted, no cross-user fetch path found; workspace RBAC with email-bound invites.
